## 第二部分：与标准 GPT-2 的架构差异

对照基准：`GPT2Config()` 实测默认值（`n_positions=1024, n_embd=768, vocab_size=50257, n_layer=12, n_head=12,
layer_norm_epsilon=1e-05, activation_function="gelu_new", tie_word_embeddings=True, scale_attn_weights=True`）。

| 维度 | 本仓库 | 标准 GPT-2（HF / OpenAI 原始） | 判定 |
|---|---|---|---|
| LayerNorm 位置 | **Pre-LN**：`x = norm1(x)` → att → dropout → `x+shortcut`（`LM:439-449`），FFN 同理（`LM:456-465`） | HF `GPT2Block.forward`：先 `self.ln_1(hidden_states)` 再 `self.attn(...)`，然后 `attn_output + residual`；ln_2 同理 | **一致**（二者都是 Pre-LN） |
| 激活函数 | **tanh 近似**：`0.5*x*(1+tanh(sqrt(2/π)*(x+0.044715x³)))`（`LM:299-302`） | transformers 5.12.0 默认 `activation_function="gelu_new"` → `NewGELUActivation.forward` 源码与上式的系数**逐字相同**；即 OpenAI 原始 TF 实现 | **一致**（与 OpenAI 原始及 HF 当前默认一致；旧版 HF 默认 `gelu` 是 erf 精确版，跨版本需注意） |
| 线性层 bias · qkv | `nn.Linear(..., bias=qkv_bias)`（`LM:80-82`）：加载/微调路径传 `True`（`LOAD:517`、`SFT:433`），**从零预训练传 `False`**（`TRAIN:537`） | Conv1D 恒有 `bias`（`Conv1D.__init__` 中 `nn.Parameter(torch.zeros(nf))`） | **加载路径一致；`TRAIN:537` 的 `False` 与 GPT-2 规格不符** |
| 线性层 bias · attn proj | `nn.Linear(d_out, d_out)` 默认 `bias=True`（`LM:86`） | `attn.c_proj` 为 Conv1D，有 bias（实测 `attn.c_proj.bias (32,)`） | **一致** |
| 线性层 bias · mlp | 两层 `nn.Linear` 均默认 `bias=True`（`LM:334,341`） | `mlp.c_fc` / `mlp.c_proj` 均为 Conv1D，有 bias | **一致** |
| 线性层 bias · ln | 自实现 `LayerNorm` 有 `scale`/`shift`（`LM:228,232`） | `nn.LayerNorm` 有 `weight`/`bias` | **一致** |
| 线性层 bias · 输出头 | `out_head = nn.Linear(emb_dim, vocab_size, bias=False)`（`LM:535`） | `lm_head` 无 bias（实测 29 个 key 中无 `lm_head.bias`） | **一致** |
| 位置编码 | **可学习** `nn.Embedding(context_length, emb_dim)`（`LM:514`），forward 中 `pos_embeds` 与 `tok_embeds` **相加**（`LM:573`） | `transformer.wpe.weight (1024, hidden)`，同样是学习式、相加 | **一致** |
| 权重共享 | **名义 tie，实际已断开**：`LOAD:361` `gpt.out_head.weight = assign(gpt.out_head.weight, params["wte"])`，`assign` 返回**一个新的 `nn.Parameter`**（`LOAD:253` `torch.nn.Parameter(torch.tensor(right))`） | HF 实测 `lm_head.weight.data_ptr() == transformer.wte.weight.data_ptr()` → **True**，是同一块内存 | **不一致**：加载后 `out_head.weight` 与 `tok_emb.weight` 数值相等但互为副本；一旦微调，二者会各自更新而漂移 |
| 注意力 vs Conv1D | `nn.Linear` 存储 `(out, in)`，加载时统一 `.T`（`LOAD:291,294,297,314,323,332`）；QKV 由 `np.split(..., 3, axis=-1)` 切分（`LOAD:283-287`） | `Conv1D.weight` 形状 `(nx, nf)` = `(in, out)`，`forward` 用 `torch.addmm(bias, x, weight)`；`c_attn` 输出按 `split(self.split_size, dim=2)` 切成 q/k/v | **数值等价**：`.T` 正好把 `(in,out)` 翻成 nn.Linear 的 `(out,in)`；切分顺序 q→k→v 也一致 |

其他细节差异（不影响权重等价，但影响数值/工程行为）：

- **掩码值**：本仓库在未缩放的 scores 上 `masked_fill_(mask_bool, -torch.inf)`（`LM:167`）后再 `/ sqrt(head_dim)`（`LM:171`）；HF 在缩放后用 `torch.finfo(dtype).min`。因果掩码下对角必然可见，无整行 -inf 的 NaN 风险，fp32 下等价；fp16 下 `-inf` 与 `finfo.min` 有差异。
- **dropout 粒度**：本仓库共用一个 `drop_rate`（注意力权重 `LM:174`、两处残差 `LM:445,462`、嵌入 `LM:517`）；HF 分 `attn_pdrop` / `resid_pdrop` / `embd_pdrop` 三个开关。
- **`context_length` 不一致**：`TRAIN:532` 用 256（自注释"非标准 1024"），而 `LOAD:515`/`SFT:431` 用 1024。前者训练出的 `model.pth` 的 `pos_emb` 只有 256 行，**与 GPT-2 权重不可互换**。
- **无 cross-attention / 无 `n_inner` / 无 `scale_attn_by_inverse_layer_idx`**：与 GPT-2 默认行为一致（默认关闭），不构成差异。
- **`unbiased=False` 方差**（`LM:251`）：与 `nn.LayerNorm` 一致。

## 第四部分：取舍建议

### 值得保留

1. **`load_weights_into_gpt` 的映射本体**（`LOAD:256-363`）。
   理由：这是全仓唯一"被真实权重验证过"的资产——QKV 切分顺序（`:283-287`）、逐层 `.T`（`:291-333`）、
   `g/b → scale/shift`（`:340-357`）三件套与实测的 HF 键名/形状完全对得上（见第三部分）。
   v2 即使改用 HF safetensors，也应把它保留为**数值对拍的 oracle**，而不是重写一遍映射。
2. **`custom_collate_fn` 的损失屏蔽语义**（`SFT:136-213`），尤其是"保留第一个 pad 位置作为 target"（`:197-198`）。
   理由：这一行是微调能不能学会停的关键，极易在重写时丢掉；其余部分（右移构造 target `:182-186`、
   `-100` 屏蔽 `:190-198`）是标准且正确的实现。
3. **`format_input` 的 Alpaca 模板契约**（`SFT:248-279`）与响应抽取（`:535`）。
   理由：prompt 模板与训练/推理必须逐字一致，属于数据契约，改动成本高于收益。
4. **`calc_loss_batch` / `calc_loss_loader` / `evaluate_model` 三段式**（`TRAIN:87/129/179`）。
   理由：接口干净（模型 + loader + device + num_batches），无副作用，可直接被 v2 的 evaluator 复用；
   `calc_loss_loader` 对空 loader 返回 NaN（`:153-154`）也算是防御到位。
5. **`generate` 的采样顺序**（`LOAD:408-435`）：先 top-k 截断再温度缩放再 `multinomial`。
   理由：该顺序与 Raschka/常见实现一致，语义正确；只需补 KV cache 与 batch 维度（`:438` 的 `.item()`）。
6. **`download_file` 的"已存在且大小一致则跳过"**（`LOAD:141-145`）。
   理由：让重复跑脚本不至于反复下载 500MB，成本低价值高。

### 必须丢弃

1. **`__main__` 里的硬编码配置**（`TRAIN:530-546`、`LOAD:509-526`、`SFT:410-446`）。
   理由：配置定义在 `if __name__ == "__main__"` 内，**无法被 import**，直接阻断任何配置化、参数化与测试；
   且三处 `context_length` 互相矛盾（`TRAIN:532`=256 vs `LOAD:515`/`SFT:431`=1024）。
2. **扁平导入 + CWD 相对路径**。
   理由：`from language_module import GPTModel`（`TRAIN:26-28`）配合 `file_path = "the-verdict.txt"`（`TRAIN:437`）、
   `models_dir="gpt2"`（`LOAD:464`）导致脚本只能在自身目录下跑，换目录就重新下载数据、输出散落；
   同时 `python -m` 完全不可用。这是"不可测、不可重入"的结构性缺陷。
3. **被破坏的权重绑定**（`LOAD:361`）。
   理由：HF 实测 `lm_head.weight` 与 `wte.weight` **同一块内存**（`data_ptr` 相等），而这里 `assign` 造的是副本
   （`LOAD:253`）。微调（`SFT:491-502`）会同时更新两个独立张量，训练后二者漂移，既浪费显存/参数量，
   又与 HF 语义不符——属于会静默出错的那类 bug。
4. **`qkv_bias=False` 的从零训练配置**（`TRAIN:537`）。
   理由：GPT-2 的 `c_attn` 恒有 bias；用这份 config 去跑 `load_weights_into_gpt` 会在 `LOAD:304-309`
   对 `None` 取 `.shape` 而崩。要么统一为 True，要么让加载器在无 bias 时显式跳过。
5. **test_mode 的 device 不一致**（`SFT:371-375` 把 `device` 绑进 collate，`:421` 又把 `device` 改成 `"cpu"`）。
   理由：在有 CUDA 的机器上 `--test_mode` 会把 batch 送到 cuda、模型留在 cpu，直接报错；所谓"快速验证"路径本身就不可信。
6. **`plot_losses` 的两份实现与"先 show 后 savefig"**（`TRAIN:362-410` + `:559` vs `SFT:282-311`）。
   理由：`TRAIN:410` 先 `plt.show()` 再在外部 `savefig`，无头环境行为不可控，且逻辑被切成两半；
   `SFT` 版只是重复代码。v2 应只保留一份、且带显式输出路径参数。
7. **`archives/` 全部 12 个文件（1053 行）**。
   理由：与 `src/modules/` 大面积重复（模型类、`assign`/`load_weights_into_gpt`、`generate`、`plot_losses`、
   分词辅助函数），且约一半正文是三引号注释掉的死代码（如 `gpt_module.py:167-228`）——它会持续误导后续维护者
   哪个才是权威实现。唯一可考虑提取的是 `gpt_download.py:48-49` 的 `backup_url` 容错（src 版 `LOAD:125` 没有）。
8. **配置字典的 in-place 修改**（`LOAD:532`、`SFT:446` 的 `BASE_CONFIG.update(...)`）。
   理由：`archives/load_pretrained_gpt_module.py:27` 是先 `.copy()` 再改的，反而是正确的；
   src 版在同一进程里二次调用会污染 `BASE_CONFIG`，与不可重入问题叠加。
9. **`tensorflow` 硬依赖**（`LOAD:24`，并因此 `SFT:327` 还要探测 TF 版本）。
   理由：仅为读取 OpenAI TF checkpoint；它让"什么都不下载的 `--test_mode`"也必须装 TF。
   v2 应改为对接 HF 权重（safetensors/pt）或一次性离线转换。
10. **无 KV cache 的整段重算生成**（`LOAD:398-402`、`GEN:55-63`）。
    理由：`max_new_tokens=256` 的测试集生成（`SFT:526`）在 355M 上是 O(n²) 全量前向，是整条流水线最慢的一段。
